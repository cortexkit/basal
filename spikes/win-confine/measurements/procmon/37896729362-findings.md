and **Untrusted `S-1-16-0`**. The integrity group is not an access group.
`OpenThreadToken` after revert returns `ERROR_NO_TOKEN` (1008); there are no Token
or unknown-type handles in the pre-input inventory. The adjustment handle is
closed before input. `primary_replacement` is null: **no second restricted-token
construction or process-primary replacement is needed** in this sequence.

At birth the actual primary and matching LPAC loader are Low; the assigned
loader is level 2. Its handle flags are 0, it is outside the inherited list,

signature `5`, image-load `7`, strict-handle `3`, extension-points `1`, and
child-process `1`; Win32k is `5` on latest and `1` on 2022. Failed class-46 LPAC
queries remain recorded as 87 / `0xc0000003`; the claim, not a fabricated getter
success, establishes LPAC.

The detached CUI flags are `0x0008000c` (extended startup, suspended, detached).
The GUI flags are `0x08080004` (extended startup, suspended, `CREATE_NO_WINDOW`,
**not** detached). Both GUI image headers are independently inventoried as
subsystem **2**, versus **3** for the CUI image. The broker remains CUI. Explicit
stdin/stdout/stderr pipes work for the GUI worker; no implicit console is required.
Its suspended console field still reads `0xfffffffffffffffd`, versus `-1` for

Within each image the GUI/CUI import inventories match: seven normal descriptors,
zero delay imports, zero non-System32 imports. No User32/GDI/Win32u worker import
was added. The GUI runtime additionally loads **System32 `apphelp.dll`** on both
images; its other measured startup modules match the corresponding detached CUI.
These are pre-probe module lists, not a post-probe census.

Both full recipes use the original inherited startup context, not the explicit
Chrome-like context. They run after the earlier context diagnostics, which
changed the disposable install-directory ACL. The final report attests the
actual worker, not that every startup ACL or inherited environment variable has
